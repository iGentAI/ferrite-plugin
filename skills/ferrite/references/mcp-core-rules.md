# Ferrite Core rules for the MCP path

The MCP-only path is self-contained: an agent with an endpoint and bearer token can build, deploy, and operate an application without a shell or CLI. These behavioral contracts cover details omitted from raw tool schemas; if a live server response differs, trust the server response.

1. Read the verdict inside the payload. Refusals set `isError: true` and identify themselves by the payload's top-level field: `Error`, `Unauthenticated`, `NotOwner`, `Rejected`, `QuotaExceeded`, `InsufficientCredit`, or `ParkRetryBlocked` (from `resume`). Negative answers arrive with `isError: false`: `validate_spec`, `code_gate`, `estimate_cost`, and `verify_domain` return a success envelope whose `passed`, `admitted`, `spec_valid`, or `verified` field is `false`, and `build_status` reports `failed`, `rejected`, or `stuck` in `state`. Inspect the body in both cases. A missing bearer token returns HTTP 401 with no JSON-RPC envelope.
2. Pass `spec` as a JSON string, not a JSON object, to `validate_spec`, `estimate_cost`, and `deploy_source`. Passing an object fails with `"EOF while parsing a value at line 1 column 0"`.
3. Omit manifest fields upstream rejects: application `auth` and `required_secrets`, route `stream_mode`, `forward_headers` on `stream` or `ws` routes, and `native` on `depends` entries. Leave `rate_limit_per_min` intact: some Core builds reject it, and where parsed its gateway enforcement is not yet verified, so `ferrite deploy` and `ferrite check --target upstream` hold specs that declare it while raw `deploy_source` does not. Never submit a spec containing `rate_limit_per_min` via raw `deploy_source`, and never strip the limit to push a deploy through; inform the user that the deploy is held. Because the parser reports one unknown field per call, clear all unsupported fields before validating. Removing `auth` exposes the app without its sign-in gate, so state that and ask first. On the raw MCP path, declare a `workload` on every service; an undeclared service consumes one-sixteenth of its plane group and can fail placement after compilation with `"FULL on the rate axis"`. Use `"workload": {"read_qps": 5, "write_qps": 5, "record_size_kb": 4, "keying": "PerKey", "hot_set_gib": 0}` (`keying` is `PerKey`, `StrictTotal`, or `Partitioned`), scaled down for small apps. `ferrite deploy` supplies a default automatically when omitted.
4. Submit each deploy once. `deploy_source` is not idempotent and does not deduplicate source: submitting the same tree twice charges two builds. Call `estimate_cost` first. Use `validate_spec` or `code_gate` when you need admission diagnostics, and avoid resending unchanged source just to repeat checks that deployment runs anyway. Keep required compilation, unit tests, and behavior checks intact. Save the submission locally, call `deploy_source` once, persist `build_id` as soon as `BuildStarted` returns, and poll `build_status {build_id, wait_s: 50}` until `deployed`, `rejected`, `failed`, or `stuck` (or poll every five seconds if `tools/list` omits `wait_s`). Builds normally take 3 to 8 minutes. Terminal states are `deployed`, `rejected`, `failed` (rolled back and refunded), `stuck` (never resubmit), `tested`, and `test_failed`. Submit a follow-up deploy only after a terminal state.
5. Reconcile lost replies before retrying. If the response to `deploy_source` drops, call `rcs_log {app}`: `deploy_source` commits `deploy <build_id>: n file(s)` as soon as the build is minted, so the build appears immediately while compilation runs. Verify via `build_status` that `app` matches `<account>/<app>`, then follow it. `account_statement` also records `deploy fee build=<id>` once charged, and is the sole trace when the source matches the previous commit (such as a redeploy to deliver a secret) because unchanged trees create no commit. Only submit again if neither log shows a build minted inside your request window. On current Ferrite Core installations, `preview_ref`, `deploy_release`, `promote`, and `rollback_release` return `BuildStarted {build_id, app}` immediately just like `deploy_source`: save `build_id`, poll `build_status`, and never resubmit mid-build. On older installations, `preview_ref` and `deploy_release` hold the connection open until completion; after a timeout there, inspect `list_apps` and `environments {app}` before retrying.
6. Treat `deployed` as registered, not live. Confirm readiness through `status` (`running`, `observed_generation`, `rollouts[].serving_generation`) and a live HTTP request. Because `generation` increments on control verbs (`scale`, `set_compute_limit`, `autoscale`), do not treat it as a deploy counter.
7. Deliver secrets through a deploy. `set_secret` and `delete_secret` take effect only on the next build and deploy; scaling to zero and back or rolling back will not inject updated secrets. Set every secret first, then deploy once. A deployment can succeed even if required secrets are missing, so application startup must fail closed when a secret is absent.
8. Guard every token. `provision` returns the bearer token once; calling it on an existing id returns `AlreadyProvisioned` with no token, and nothing reissues it. Rotate credentials with `rotate_token` followed by `confirm_token` using the new token, contain leaks with `revoke_other_tokens`, and inspect active credentials via `credentials`. After claiming the account through `claim_url`, the owner can mint additional named tokens in Dashboard Settings > API tokens and import the copied private TOML file with `ferrite login --credentials-file PATH`, which leaves other installations unaffected and individually revocable.

   After `provision_ephemeral`, save both the operating `token` and the transfer `claim_token` privately. To keep a trial, open it in the Dashboard, or join an account the person already owns, give them the current account's private `claim_url`: on a trial started by the CLI or a connector, it offers **Keep this as my account** (a permanent account of their own with the same apps, URLs and data and a new, readable ID) or **Move it into** their existing account (see [keep, move and join](mcp-operations.md#dashboard-sign-in-and-durable-transfer)). A trial opened with `provision_ephemeral` keeps its deadline after an owner links, so its apps are kept by moving them with `claim` and the saved `claim_token`. A connector or remote server that signs in through the browser never calls `provision` or `provision_ephemeral`. Authenticate subsequent trial calls with the operating token, since provisioning does not swap the client's active bearer automatically. Prefer private client credential storage. A hosted MCP client sending no `Authorization` bearer can pass the supported `token` argument on account-scoped calls (see [MCP authentication](mcp-operations.md#ephemeral-account-authentication)); a conflicting existing bearer must be removed via client config or isolated on a separate connection. Never place tokens in prose, source files, URLs, or shared logs.
9. Remember public base-domain assumptions. `https://<host>/`, `claim_url`, and `billing_portal` URLs assume public routing and are unreachable on a local fleet, where the gateway listens on plain HTTP and routes by `Host` header. `billing_portal`, `claim_url`, and `set_notify_channel` depend on fronts that local fleets do not run.
10. Design within measured runtime bounds: 262,144-byte request body, 16 KiB request head (at most 64 headers), 16 response headers with at most one `set-cookie`, 8 s API deadline (HTTP 504 on expiry), 4 MiB API response budget, egress replies capped near 1 MiB with a 10 s timeout, no response headers, and no redirects. `OPTIONS`, `HEAD`, and `TRACE` never reach `api` route handlers.

Without a writable shell and CLI, deploy through hosted MCP `deploy_source`. Run free manifest and code gates when diagnostics help, submit once, follow the returned receipt, and reconcile lost replies through `rcs_log` before creating another deployment.
