# CLI workflows

## Discover

Run `ferrite --help` and `<subcommand> --help` for the exact command surface; the installed binary is authoritative. `ferritectl` is a platform-operator binary and must not substitute for the customer `ferrite` CLI.

## Create and develop

```sh
ferrite new --with-tests alloy my-app
cd my-app
ferrite check --json
ferrite test
ferrite dev
```

Choose `alloy` (routing, documents, and actions; default choice for HTML apps), `hello` (request/reply API), or `webapp` (content, API, and SSE live page). `ferrite new` generates an upstream Ferrite Core manifest by default; never pass `--target fork`, which exists solely for the archived fork. For an Rsx application, scaffold with `ferrite rsx new <name>` and compile or verify its `app/` tree with `ferrite rsx sync` and `ferrite rsx check`.

Add shared subsystems with `ferrite add <name>`, which vendors a registry source package under `src/<mount>/` and records it in `ferrite-packages.json`. Run `search_docs "packages"` or MCP `list_packages` (when present in `tools/list`) to browse published packages. Pass `--registry <url>` or `--path <checkout>` to select an alternate source, and `--force` to overwrite modified files (without `--force`, differing files are listed and nothing is overwritten). The CLI verifies the registry index signature before writing any file and trusts the `https://packages.ferrite.cloud` and `https://packages.ferrite.build` signing identity (`key_id` `a2802db62e77cf7a`) automatically. Treat `SIGNATURE CHECK FAILED` or an untrusted-signer error as a real security failure to report, never something to bypass with `--allow-unsigned-registry` or `FERRITE_REGISTRY_KEYS`.

`ferrite dev` prints its local URL alongside Rust compilation, content refresh, restart, and readiness events. Its gateway binds `127.0.0.1` only, so any displayed network address is unreachable from another host, and an occupied `--port` exits with an error instead of silently picking a different port. Pass `--json` for one lifecycle event per line. Keep the process attached: during an agent build, start it at most once, verify valid and invalid paths, and stop that exact process before deploying. On a compile error, edit the source and let hot reload recover instead of spawning a second server.

## Streaming replies

For SSE or WebSocket replies, import `ferrite_app::FramePublish` and invoke `frames.publish_frame(&frame).await` on the queue bound for `reply_to`. Send typed `StreamFrame` values; the SDK tracks sequence numbers and resolves uncertain publications before advancing to the next frame. Standard HTTP responses use the regular reply path. Close the stream with `done: true` and send no frames afterward. If an older scaffold carries a stale SDK, run `ferrite twin` to compare it against the twin bundled with the current CLI.

## Authenticate and deploy

```sh
ferrite account
ferrite check --target upstream --remote --json
ferrite cost --instances 1
ferrite deploy
ferrite status my-app
```

Share the monthly estimate and deploy fee returned by `ferrite cost` with the user before running `ferrite deploy` (`SKILL.md`, "Before you build"). The quote reflects the connected installation's live tariff and does not install a hard spending cap by itself.

Preserve whatever working account `ferrite account` reports. Only when no login is configured, authenticate with `ferrite login --endpoint <url> --ephemeral` (a trial with $5 of credit, enough to run an app or a few for 48 hours, that deploys immediately; its apps go offline at the server's `expires_at_ms` unless the person signs in through its `claim_url` link), `ferrite login --sign-in` (browser sign-in with Google or GitHub to an account the person already owns), `ferrite login --endpoint <url> --id <account>` (a new durable account), or `ferrite login --credentials-file <path>` (an owner-only TOML credential file). Never overwrite a working login to mask an endpoint mismatch.

`ferrite check --remote` executes the authoritative remote code and spec gates free of charge, while `ferrite check --target upstream` catches offline every manifest field and SDK symbol upstream Core rejects. `ferrite deploy` stages an upstream projection of `ferrite.json` and `Cargo.toml` under `.ferrite/upstream-projection/` (leaving your files untouched), submits source once via `deploy_source`, follows `build_status`, and waits on `status` until the new generation serves. It refuses manifests carrying `auth` or `stream_mode` unless `--drop-auth` or `--drop-stream-mode` explicitly consents, and strips `required_secrets` automatically. It leaves `rate_limit_per_min` intact and holds rate-limited manifests without verified gateway enforcement; exact-spec validation is necessary, and gateway adoption plus a real exhausted-budget `429` prove enforcement, so never drop the limit to bypass the hold. Because `deploy` does not issue an HTTP request to your app, fetch a live route yourself before declaring success. Unchanged trees skip submission unless `--force` is passed. Never serialize a local workspace into raw MCP calls when the CLI is present, and never start a second `deploy` while a build is active, as each `deploy_source` call charges a build.

Set the shell timeout on `ferrite deploy` to at least 20 minutes; attested remote builds outlive a two-minute tool default. When a shell tool returns a running session handle, poll that exact handle until `ferrite deploy` exits; a spawn acknowledgement is not completion, and `status` must not race an in-flight deploy. If the tool disconnects or interrupts the command, reconcile with `ferrite deploy resume --attempt ATTEMPT_ID` using the journaled attempt ID printed on submission (omit `--attempt` to resume the latest unfinished attempt). Keep the source tree, endpoint, account, and local journal intact so recovery reconciles the original operation.

## Observe and operate

CLI read commands are `account`, `status <app>`, `logs <app>`, `usage [app]`, `host` (public origin and OAuth callbacks, known ahead of first deploy), `cost` (pre-deploy quote), `statement` (metered charges and remaining balance), and `domains list` / `domains check`. Remote write commands are `deploy`, `preview`, `fork`, `withdraw <app>`, `domains add`, `secrets`, `tasks`, `claim`, and `ferrite rcs` (`clone`, `pull`, `checkout`, `status`, `commit`, `push`, `log`, `branch`, `branches`, `merge`, `land`, `remote`) for the hosted repository. Fall back to Ferrite MCP for control-plane reads or actions absent from the installed CLI's `--help`. Read help output and confirm impact before running any remote mutation.

Secrets use `ferrite secrets set <NAME>` reading from stdin (or `--value-file <path>`), `ferrite secrets list` (names only, never values), and `ferrite secrets delete <NAME>`, each accepting `--app` just like `status`. MCP `set_secret {app, name, value}`, `list_secrets {app}`, and `delete_secret {app, name}` perform the same actions. Never pass secret values in argv or commit them into source. Once stored, a secret cannot be read back; the runtime injects it into the app process, whose egress policy restricts outbound destinations to declared hosts. Ensure application code never logs, echoes, or persists secret values. Updated secrets reach workers only on the next deploy, and `ferrite deploy` submits a full build after a secret change even when source files did not change; set all secrets first, then deploy once.

To reach an account the person already owns from another computer, run `ferrite login --sign-in`: the browser opens Ferrite's sign-in, the person continues with Google or GitHub, picks the account and clicks **Allow**, and the CLI saves a named login for this computer that the Dashboard lists and can revoke. Do not run `ferrite agent connect` or `ferrite agent recover`; Ferrite Core does not serve them, and `agent connect` exits with `AGENT_SETUP_UNSUPPORTED_PLATFORM` without saving state. To start fresh, open an account directly with `ferrite login --ephemeral` (a trial account that deploys immediately; its apps go offline at the server's `expires_at_ms` unless the person signs in) or `ferrite login --id <name>` (a durable account, whose credit is bought in the Dashboard). Check the server response and `ferrite account` for the active lifetime and balance instead of assuming fixed values. See `SKILL.md`, "Accounts, trials and running cost", for Ferrite Cloud trial bounds and zero-balance behavior.

MCP `claim_url` issues a single-use browser link for an account with no owner. After Google or GitHub sign-in it offers **Keep this as my account**, which makes an `eph-` trial a permanent account of the person's own (same apps, URLs and data, no deadline; the account ID changes from `eph-…` to a readable one), or **Move it into** an account that identity already owns. Either way the trial's CLI login follows: `ferrite account --json` then answers for the new account and reports `trialFollow`, and `ferrite mcp-serve` answers one refused call with `TRIAL_LOGIN_FOLLOWED` before using the new login. To move a trial's apps from the terminal instead, run `ferrite claim` from the trial profile: it provisions a durable account, migrates the apps, stores the new credential privately, and prints the dashboard link (`--json` returns the account, app IDs, and link). Pass `--into <path>` with a private credential file to move apps into an existing durable account. Without the CLI, follow the [hosted MCP transfer](mcp-operations.md#dashboard-sign-in-and-durable-transfer). Durable accounts carry no 48-hour expiry. An account's initial credential is issued once to the caller that provisioned it; another computer joins the account with `ferrite login --sign-in`.

## Add app user authentication

Keep `ferrite login` (your developer Ferrite Cloud account) distinct from end-user sign-in inside the application. For application users, read `auth-workflows.md` and run `ferrite add auth` instead of writing a custom identity layer. `ferrite auth` is a retired verb that points to that package.

`ferrite add agent-ready` adds password-change discovery advertising only routes served by your app. Dispatch through `handle_h`, forward all headers it returns, and follow [Auth workflows](auth-workflows.md). In local MCP, `local_add` installs the package and returns the source wiring steps for the agent to apply.

## Local project rules

Set the shell timeout for `ferrite deploy` to at least 20 minutes. Attested builds typically run 3 to 8 minutes and outlast a two-minute agent tool default even when progressing normally. If the shell tool returns a running process handle, keep polling it until it exits; a spawn acknowledgement is not deployment completion. If the command is interrupted or detached, run `ferrite deploy resume --attempt ATTEMPT_ID` using the journaled attempt ID printed at submission (or omit `--attempt` for the latest unfinished attempt in the project). Never pass a build ID to `--attempt`. Use `ferrite deploy status` for a single read and `ferrite deploy wait` to follow progress. Exit code `3` signals an uncertain outcome: `resume` reconciles against `rcs_log` and `account_statement` without double-submitting. Keep the source tree, project journal, endpoint, and account intact instead of launching a second deploy.

Ship early and iterate: once a deployment serves verified traffic, share the live URL before polishing and land refinements in follow-up deploys.

Before modifying an application that already serves users, or to inspect historical state before an incident, fork it first: `ferrite fork <copy>` (MCP: `fork`, or `remote_fork` via `ferrite mcp-serve`) creates a separate application at its own host with the live code and a point-in-time snapshot of all data (`--as-of <time>` for an earlier timestamp) without touching production. Edit the fork from a clean copy of the workspace (excluding `.ferrite/` and `target/`) whose `ferrite.json` names the fork; `ferrite test` and `ferrite deploy` there update the copy and preserve its data. Deploying a copied folder under a new name without forking produces an empty app.

Manage secrets with `ferrite secrets set <NAME>` (value via stdin, for example `printf %s "$VALUE" | ferrite secrets set auth_allow`), `ferrite secrets list`, and `ferrite secrets delete <NAME>` (MCP: `set_secret {app, name, value}`, `list_secrets {app}`, and `delete_secret {app, name}`). Because secrets reach workers only through a build, `ferrite deploy` runs a full charged build after a secret update even when source files did not change; set all secrets first and deploy once. Verify with `ferrite secrets list` and test that the live app reads them. Never `withdraw` a serving app to rotate or update configuration; redeploy in place.

An app using the `auth` package deploys in one pass. Because the platform derives the hostname deterministically from the app id, the public origin and OAuth callback URLs are known ahead of deployment: after `ferrite add auth`, run `ferrite host` to print the origin and callback URLs, register those callbacks with the OAuth provider, set every secret listed by `ferrite add auth` (`ferrite secrets set <NAME>` on stdin; generate a fresh session secret via `openssl rand -base64 48 | ferrite secrets set auth_session_key`), and run `ferrite deploy` once. Deployment refuses with `DEPLOY_AUTH_SECRETS_MISSING` while any required auth secret is unset; do not bypass it with `--allow-missing-secrets`. Over MCP without `app_host`, derive the hostname as documented in `mcp-operations.md`, or deploy once to read the host, set secrets, and deploy once more.

Use the local loop for compiler and test feedback. Pass `ferrite check` and `ferrite test` before the first remote build, and run `ferrite dev` when runtime or browser behavior needs verification. Never spend a remote build catching Rust, SDK, gate, or manifest errors that the local CLI detects immediately. Remote gates and live read-back remain the final verdict.

Before running `check` and `test`, turn the user's request into a brief acceptance checklist and audit the implementation against it. Include every requested input, choice, output, optional control ("optional" means optional to fill, never omitted), privacy rule, and invalid or boundary case. For forms and calculators, isolate pure business logic so unit tests in `src/` cover valid cases alongside every named invalid and boundary class. Invalid input must clearly refuse computation, state what to fix, and never leave stale results visible. Native HTML `min`, `required`, and `type` checks count, but verify interactions carefully: `min="0.01"` paired with `step="0.1"` marks `10` invalid because step increments count from `min`; use `step="any"` for measurements. When extending integration tests, stick to the scaffold's exact `ferrite-app-test` types and methods instead of inventing harness helpers. Run `ferrite test` directly and fix every failure before deploying. When `ferrite dev` is warranted, start it once, test both valid and invalid inputs on the rendered page, and stop that exact process before deploying. Compiling cleanly does not prove functional correctness.

Treat the scaffold's vendored SDK as toolchain input: avoid reading or editing `vendor/`, generated build files, Cargo output, or full lockfiles to reverse-engineer APIs. Edit only `src/`, `site/`, tests, and `ferrite.json`, and rely on `search_docs`, `read_docs`, and compiler diagnostics. For vendored packages (`src/auth/`, `src/alloy/`), read their `SETUP.md` or README before reading their source. For the minimal Ferrite Core skeleton and InfraSpec, call `read_docs {doc: "quickstart"}`; its `IngressReply` carries `correlation_id`, `status`, `body`, and `headers`.

When an application requires user sign-in, preserve it unconditionally. Never strip `auth`, expose a signed-in user's data publicly, or deploy an unprotected clone just to produce a link; if OAuth configuration cannot be finished, stop after the green local loop and report what is missing.

`ferrite preview` commits the workspace and deploys it to a temporary host. Previews run the same build and admission checks as deploys, skip the test-verdict gate, incur no charge, create no release, and expire automatically after two hours. Treat `ferrite deploy` as a billable remote mutation that requires user intent. In automated scripts, pass `--json` wherever the command supports it.

Record the account token, app id, build id, and returned host. Never launch a concurrent build, resubmit unchanged rejected source, or swap the requested app for a connectivity probe. On a gate rejection, inspect the error code (`ferrite explain CODE` or `explain_gate`), patch the existing project, re-run both free gates, and retry the same app.
